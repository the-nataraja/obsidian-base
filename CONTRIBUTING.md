# Регламент ведения репозитория и контрибьютинга

Добро пожаловать в регламент совместной работы над нашей базой знаний! Данный документ является **строгим техническим стандартом**. Наша цель — поддерживать репозиторий в идеальном порядке, чтобы каждый конспект было легко найти, удобно читать (на сайте `notes.vlsu-hub.org`, на GitHub и в Obsidian) и чтобы в базе не было «битых» ссылок или сломанной верстки.

---

> [!IMPORTANT]
> **Автоматическая проверка (CI/CD Бот)**
>
> Наш репозиторий защищен автоматическим Python-скриптом (ботом). Бот запускается каждый раз, когда вы создаете **Pull Request (PR)**.
>
> * Бот анализирует список файлов через `changed_files.txt`. Это значит, что он проверяет **только те файлы, которые вы изменили или добавили**. Вас не заблокируют за чужие старые ошибки.
> * Проверка выполняется с помощью жестких регулярных выражений (RegEx) и парсеров.
> * Если скрипт находит хотя бы одну ошибку (превышен размер, неверное имя файла, забытое поле в шапке), он прерывает работу с кодом `sys.exit(1)`, и ваш PR получает красный крестик ❌. Слияние с основной базой блокируется.
> * **Защищенные файлы:** Любое изменение системных файлов `.gitignore`, `CONTRIBUTING.md` или `README.md` вызовет системное предупреждение `::warning::` в логах CI/CD. Делайте это только по согласованию с администраторами базы.

## ЧАСТЬ 1. Git Workflow и отправка конспектов

В проекте участвуют не только программисты, поэтому мы настоятельно рекомендуем использовать визуальный клиент **GitHub Desktop**. Это минимизирует шанс случайно затереть чужую работу или запутаться в ветках (но если что, мы все поправим, не волнуйтесь).

### Терминология

* **Upstream (Главный репозиторий):** Общая база знаний группы/курса. Писать напрямую туда нельзя.
* **Origin (Ваш Форк):** Ваша личная копия главного репозитория в вашем аккаунте GitHub. Вы работаете в ней.

---

### 1.1. Основной алгоритм (GitHub Desktop / Windows & macOS)

#### Шаг 1. Создание форка (Один раз)
Зайдите на страницу *Главного репозитория* (upstream) в браузере. В правом верхнем углу нажмите кнопку **`Fork`**. Оставьте копирование основной ветки `main` и создайте копию в своем аккаунте.

#### Шаг 2. Скачивание базы на ПК
Откройте программу GitHub Desktop. В верхнем меню выберите `File -> Clone repository`. Перейдите на вкладку `GitHub.com`, найдите в списке **свой форк** (он будет называться `ваш-ник/название-репо`) и нажмите `Clone`.

#### Шаг 3. Подключение Obsidian
Запустите Obsidian. Нажмите `Open folder as Vault` (Открыть папку как хранилище) и выберите папку, которую только что скачал GitHub Desktop.

#### Шаг 4. 🔴 СИНХРОНИЗАЦИЯ (Делать каждый раз перед работой!)
Пока вы спали, другие студенты могли добавить новые лекции. Если вы начнете писать без обновления, возникнет *Merge Conflict*.

1. Откройте GitHub Desktop.
2. Вверху нажмите **`Fetch origin`**.
3. Если в главном репозитории были изменения, программа предложит вам `Pull origin` или `Pull from upstream`. Обязательно подтвердите это, чтобы скачать свежие файлы на свой ПК.

#### Шаг 5. Работа над конспектом
Создайте файл в нужной папке (структуру см. в Части 2), заполните его и сохраните. Obsidian сохраняет файлы автоматически.

#### Шаг 6. Сохранение (Commit)
Перейдите в GitHub Desktop. Слева вы увидите список измененных вами файлов.

В левом нижнем углу напишите название правки в поле *Summary*. Используйте понятную семантику:
* `feat: добавлен LEC-03 по матану` (добавление нового материала)
* `fix: опечатка в LAB-02` (исправление)

Нажмите синюю кнопку **`Commit to main`**.

#### Шаг 7. Отправка на сервер (Push)
Нажмите кнопку **`Push origin`** в верхней панели. Теперь ваш файл находится в вашем форке на сервере GitHub.

#### Шаг 8. Создание Pull Request
Зайдите на страницу *Главного репозитория* в браузере. GitHub автоматически увидит, что в вашем форке появились новые данные, и покажет желтую плашку с кнопкой **`Compare & pull request`**. Нажмите её, оставьте комментарий и нажмите `Create pull request`. Бот начнет проверку!

---

### 1.2. Консольный Git (Linux / Продвинутые пользователи)

Если вы работаете через терминал, ваш воркфлоу выглядит следующим образом.

Настройка upstream (выполняется один раз после клонирования форка):

```bash
git remote add upstream git@github.com:vlsu-hub/obsidian-base.git
```

Повседневная работа:

```bash
# 1. Забираем актуальные изменения из общей базы
git fetch upstream

# 2. Вливаем их в свою локальную ветку main
git checkout main
git merge upstream/main

# 3. Пишем конспект в Obsidian...

# 4. Индексируем изменения
git add .

# 5. Делаем осмысленный коммит
git commit -m "feat: добавлен LEC-05 по физике"

# 6. Отправляем в СВОЙ форк (origin)
git push origin main
```

После этого переходите в браузер и создавайте Pull Request.

---

### 1.3. Что делать, если бот заблокировал PR? ❌

Если после создания Pull Request вы увидели красный крестик (Checks failed):

1. **НЕ закрывайте (Close) этот Pull Request!** Вам не нужно создавать новый.
2. Нажмите на кнопку **`Details`** рядом с упавшей проверкой.
3. В открывшемся логе консоли найдите строчки, начинающиеся с `[!] ОШИБКА ВАЛИДАЦИИ`. Бот напишет точную причину, например: `[LEC-01_Физика.md] Ошибка в имени файла. Разрешены только строчные латинские буквы, цифры и '_'...`
4. Вернитесь в Obsidian на своем ПК и исправьте эту ошибку (например, переименуйте файл на английский).
5. Откройте GitHub Desktop (или консоль), сделайте новый коммит (например, `fix: исправил имя файла для бота`) и нажмите **Push**.
6. GitHub **автоматически** подтянет этот коммит в ваш уже открытый PR, и бот запустит проверку заново!

## ЧАСТЬ 2. Файловая система, Именование и Метаданные

Строгая организация файлов необходима для корректной генерации ссылок на сайте (Quartz) и удобной навигации внутри хранилища Obsidian. Проверяющий скрипт анализирует пути к файлам и их содержимое с помощью регулярных выражений (RegEx).

> [!IMPORTANT]
> **Язык и запрет транслита**
>
> Чтобы URL-адреса на сайте выглядели чисто и корректно работали во всех операционных системах, **все названия папок и тем файлов пишутся строго на английском языке**.
>
> * **Транслит запрещен** (нельзя писать `zakony_nyutona` или `mehanika`). Если не уверены в переводе термина — воспользуйтесь переводчиком.
> * Единственное исключение для транслита — **фамилии преподавателей** в названиях папок третьего уровня.

---

### 2.1. Структура директорий

Файловое дерево строится по принципу строгой вложенности. Пути проверяются по следующим правилам:

1. **Первый уровень (Семестры):**  
   Формат `<номер>-sem` (например, `1-sem`, `2-sem`).
2. **Второй уровень (Дисциплины):**  
   Название предмета на английском в `snake_case` (например, `physics`, `math`, `defense_basics`, `russian_statehood`).
3. **Третий уровень (Тип занятий и преподаватель):**  
   Формат: `<цифра>-<ПРЕФИКС>_<ФамилияИО>` (для рейтингов и экзаменов в конце **обязательно** указывается год: `_<ГОД>`).
   * Ведущая цифра задает принудительную логическую сортировку папок вместо алфавитной.
   * Фамилия и инициалы преподавателя пишутся транслитом в `CamelCase` без пробелов и скобок.
   * ✅ *Правильно:* `1-LEC_MalyshevaDA`, `2-SEM_MorozovMV`, `3-LAB_MalyshevaDA`, `4-TST_MalyshevaDA_2026`, `5-EXM_MakarovaOV_2026`.
   * ❌ *Неправильно:* `1_лекции (Малышева ДА)`, `LEC_Malysheva`, `4-TST_MalyshevaDA` *(забыт год для рейтинга)*.
4. **Четвертый и последующие уровни (Опционально):**  
   При необходимости внутри папки типа занятий можно создавать тематические или нумерованные подпапки на английском (например, `1_mechanics`, `0_topics_review`).
5. **Папки для медиафайлов:**  
   Любые изображения обязаны находиться строго внутри подпапки `attachments/` рядом с конспектами (в текущей папке с `.md`-файлами). Размещение картинок в корне предмета запрещено.
6. **Индексные файлы:**  
   В каждой папке (от корня репозитория до подпапок) создается единый индексный файл `_index.md` — на сайте он выступает в роли главной страницы раздела. Файлы, начинающиеся с `_`, пропускаются ботом при проверке префиксов.

---

### 2.2. Стандарт именования файлов (КРИТИЧНО)

Имена учебных markdown-файлов проверяются регулярным выражением:
```regex
^(LEC|SEM|LAB|TST|EXM)-(\d{2})_([a-z0-9_]+)\.md$
```

Любое отклонение от этого формата вызывает ошибку валидации.

1. **Префикс (только заглавные буквы):**  
   Допустим строго один из пяти вариантов:
   * `LEC` — Лекция / конспект лекции
   * `SEM` — Практическое занятие / семинар
   * `LAB` — Лабораторная работа
   * `TST` — Рейтинг / контрольная работа
   * `EXM` — Экзаменационный билет или материал
2. **Номер (через дефис `-` после префикса):**  
   Две цифры с ведущим нулем (`00` для вводных лекций, `01`, `02`, `10`, `15`).
3. **Тема (через нижнее подчеркивание `_` после номера):**  
   * **Формат:** строго английский язык в `snake_case`.
   * ✅ **Разрешены:** строчные латинские буквы (`a-z`), цифры (`0-9`) и нижние подчеркивания (`_`).
   * ❌ **Запрещены:** кириллица, транслит, заглавные буквы, пробелы и дефисы.

> [!NOTE]
> **Примеры именования файлов**
>
> * ❌ `LEC-01_Законы_Ньютона.md` *(ошибка: кириллица и заглавные буквы)*
> * ❌ `LEC-01_zakony_nyutona.md` *(ошибка: транслит запрещен)*
> * ❌ `LEC 01 - newtons laws.md` *(ошибка: пробелы и неверный разделитель)*
> * ❌ `SEM-1_integrals.md` *(ошибка: нет ведущего нуля в номере)*
> * ✅ `LEC-00_introduction_to_mechanics.md`
> * ✅ `LEC-01_newtons_laws.md`
> * ✅ `SEM-05_first_law_of_thermodynamics.md`

**Кодировка:** Файлы должны быть сохранены строго в кодировке **UTF-8**. Obsidian делает это по умолчанию, однако при использовании сторонних редакторов (например, Блокнот Windows) файл может сохраниться в Windows-1251. Бот не сможет его прочитать и выдаст ошибку `UnicodeDecodeError`.

---

### 2.3. Метаданные (YAML Frontmatter)

Каждый учебный markdown-файл обязан начинаться со служебного блока YAML. Бот извлекает этот блок и проверяет его структуру. Отсутствие шапки или синтаксическая ошибка в YAML приведет к отклонению файла.

*(Исключение: в индексных файлах `_index.md` указывается только поле `title`, а в корневых системных файлах `README.md` и `CONTRIBUTING.md` YAML-шапка не используется).*

**Эталонный пример YAML-шапки:**

```yaml
---
title: LEC-00 введение в механику
date: 2026-09-02
tags:
  - author/DocteurD
  - typer/the-nataraja
---
```

**Правила заполнения полей:**

* **`title`** *(Обязательно)*  
  Читаемое название конспекта на русском языке в формате `<ПРЕФИКС>-<НОМЕР> <название>`. Именно это поле отображается на сайте, в заголовке вкладки Obsidian и используется как текст при ссылках на файл.
* **`date`** *(Обязательно для конспектов)*  
  Дата фактического проведения занятия в стандарте ISO 8601: `YYYY-MM-DD`. Использование точек или слешей (например, `02.09.2026`) вызовет ошибку скрипта.
* **`tags`** *(Массив ролей, обязательно для конспектов)*  
  YAML-массив (список с дефисами `- `), в который записываются участники подготовки материала:
  * 🔴 `author/username` — **(Обязательно)** Кто изначально написал конспект от руки (на паре). Авторов может быть несколько.
  * 🟡 `typer/username` — Кто набрал текст в Markdown и оформил материал для репозитория:
    * Если автор один и он же набрал конспект, тег `typer/` **не пишется**.
    * Если автор и наборщик — разные люди, тег `typer/` **обязателен**.
    * Если авторов (`author/`) **несколько**, тег `typer/` **обязателен** (указывается тот, кто объединил конспекты и выложил итоговый файл, даже если он является одним из авторов).
  * 🟢 `editor/username` — **(Опционально)** Кто позже исправлял или дополнял уже выложенный в репозиторий конспект. Редакторов может быть несколько.

**Пример, когда автор сам набрал конспект:**
```yaml
---
title: LEC-01 кинематика
date: 2026-09-09
tags:
  - author/DocteurD
---
```

**Пример с несколькими авторами и редактором:**
```yaml
---
title: LEC-02 динамика
date: 2026-09-16
tags:
  - author/DocteurD
  - author/user2
  - typer/DocteurD
  - editor/the-nataraja
---
```

> [!WARNING]
> **Запрет смысловых тегов в YAML**
>
> В блоке метаданных допускаются **только** теги ролей (`author/`, `typer/`, `editor/`). Попытка добавить предметный или статусный тег (например, `- физика` или `- важно`) прямо в шапку приведет к ошибке валидации.

## ЧАСТЬ 3. Style Guide: Оформление конспектов (Markdown + LaTeX)

Единообразие визуального стиля критически важно для читаемости базы знаний на сайте `notes.vlsu-hub.org`, в веб-интерфейсе GitHub и в приложении Obsidian. Приведенные ниже правила проверяются скриптом и обязательны к исполнению.

### 3.1. Иерархия заголовков и пустые файлы

Проверяющий скрипт очищает текст от блоков кода, после чего анализирует структуру заголовков и наличие осмысленного текста.

* **Пустые файлы:** Файл не может состоять только из YAML-шапки. Бот ищет буквенно-цифровые символы (RegEx: `[a-zA-Zа-яА-Я0-9]`). Если текст конспекта отсутствует, выдается ошибка.
* **Заголовок первого уровня (`# `):** Использовать `# ` (H1) в начале тела документа **не рекомендуется**, особенно если его текст совпадает или дублирует поле `title` из YAML-шапки. Главный заголовок страницы на сайте формируется из `title` автоматически. Начинайте конспект сразу с основного текста или разделов `## `.
* **Структура:** Для крупных разделов применяется заголовок второго уровня (`## `), для подразделов — третьего (`### `).
* **Разделители:** Перед каждым новым крупным разделом (`## `) рекомендуется ставить горизонтальный разделитель (три дефиса `---` на пустой строке) для визуальной разгрузки текста.

---

### 3.2. Оформление формул (MathJax / LaTeX)

Для записи математических и физических выражений использование обычного текста (вида `A = F * S / t`) не допускается. Применяется синтаксис LaTeX:

* **Внутристрочные переменные:** Оборачиваются в одинарные знаки доллара `$ ... $`.  
  *Пример:* Масса $m$ умножается на скорость $\vec{v}$ (`$\vec{v}$`).
* **Блочные уравнения:** Оборачиваются в двойные знаки доллара `$$ ... $$` и располагаются по центру.
* 🔴 **Важное правило рендеринга:** Блочные формулы должны отделяться от основного текста **пустыми строками** сверху и снизу. В противном случае парсер GitHub и сайт могут склеить формулу с текстом, нарушив отображение.

---

### 3.3. Блоки кода и защита от поломки верстки

В репозитории работает строгая проверка на незакрытые блоки кода (функция `has_unclosed_code_blocks`).

* Любой блок кода, начатый тройными обратными кавычками ```` ``` ```` или тильдами ```` ~~~ ````, обязан иметь закрывающую пару.
* Незакрытый блок кода «поглощает» весь последующий текст документа, ломая рендеринг Markdown и скрывая заголовки от парсера. При обнаружении незакрытого блока бот немедленно блокирует слияние.

---

### 3.4. Запрет тегов внутри текста

В репозитории действует строгий запрет на хештеги в теле документа: **любые теги внутри текста конспекта (например, `#важно`, `#дописать`, `#экзамен`, `#кинематика`) строго запрещены.**

* Теги допустимы **исключительно** в YAML-шапке и **только** для указания ролей участников (`author/`, `typer/`, `editor/`).
* Обнаружение в тексте любого тега, начинающегося с `#` без пробела (и не находящегося внутри блока кода), вызывает ошибку валидации. Для поиска по базе используется встроенный полнотекстовый поиск сайта и Obsidian.

---

### 3.5. Внутренние ссылки (Wikilinks)

Поскольку имена файлов и папок написаны на английском, при создании внутренних ссылок `[[...]]` действуют строгие правила:

* **Обязательный русский алиас:** После вертикальной черты `|` обязательно указывается отображаемое название на русском языке, иначе на сайте вместо него будет отображаться английское имя файла.
* **Точное совпадение с `title`:** Текст алиаса должен браться **строго из поля `title`** того файла (или `_index.md` папки), на который вы ссылаетесь — вместе с префиксом и номером, чтобы не возникало путаницы с названиями.

> [!NOTE]
> **Примеры вики-ссылок**
>
> * ❌ `[[LEC-00_introduction_to_mechanics]]` *(ошибка: нет русского алиаса)*
> * ❌ `[[LEC-00_introduction_to_mechanics|введение в механику]]` *(ошибка: потерян префикс и номер из `title`)*
> * ✅ `[[LEC-00_introduction_to_mechanics|LEC-00 введение в механику]]`

### 3.6. Текстовые акценты и Коллауты (Выноски)

Для выделения важной информации применяется синтаксис Callouts, который поддерживается на сайте, на GitHub и в Obsidian. Заголовок выноски оформляется на следующей строке после типа блока, чтобы он корректно отображался на GitHub.

* **Термины и определения:** Оформляются стандартной цитатой (`> `).
  ```markdown
  > **Механическая система** — совокупность материальных точек...
  ```
* **Законы, теоремы и правила:** Оформляются блоком `[!IMPORTANT]` (или `[!INFO]`).
  ```markdown
  > [!IMPORTANT]
  > **Закон сохранения импульса**
  >
  > Суммарный импульс замкнутой системы сохраняется во времени...
  ```
* **Примечания преподавателя:** Оформляются блоком `[!NOTE]`.
  ```markdown
  > [!NOTE]
  > **Пояснение**
  >
  > Это работает только для замкнутых систем.
  ```

Для акцентирования внимания внутри абзацев используется:
* **Жирный шрифт** (`**текст**`) — для ключевых слов.
* **Подсветка маркером** (`==текст==`) — для фокуса на критичных деталях (отображается как маркерный фон).

## ЧАСТЬ 4. Работа с медиафайлами и системные ограничения

Для сохранения работоспособности репозитория, высокой скорости загрузки сайта и предотвращения бесконтрольного роста базы, проверяющий бот накладывает строгие ограничения на загружаемые файлы и пути к ним.

### 4.1. Абсолютные и локальные пути (КРИТИЧНАЯ ОШИБКА)

**Категорически запрещено использование локальных (абсолютных) путей к файлам!**  
При перетаскивании изображения в редактор из системных папок может сгенерироваться ссылка, привязанная к файловой системе конкретного компьютера. Такая ссылка будет работать только у вас, а у остальных пользователей и на сайте отобразится ошибка рендеринга.

Бот парсит все стандартные ссылки `[]()` и вики-ссылки `[[]]` и немедленно отклоняет PR, если обнаруживает следующие паттерны:
* Протокол локального файла: `file://...`
* Буквы дисков Windows: `C:\...`, `D:/...`
* Системные директории UNIX/macOS: `/Users/...`, `/home/...`, `/root/...`, `/tmp/...`
* Сетевые пути: `\\...`

**Правильная настройка Obsidian:**  
Для автоматической генерации относительных путей настройте клиент Obsidian:
1. Перейдите в `Settings` (Настройки) -> `Files & Links` (Файлы и ссылки).
2. Параметр `Default location for new attachments` установите в значение **`In subfolder under current folder`**.
3. В появившемся поле `Subfolder name` укажите **`attachments`**.

---

### 4.2. Стандарт именования и подготовки изображений

Все изображения перед добавлением в папку `attachments/` должны соответствовать следующим требованиям:

1. **Формат:** строго **`.webp`**. Загрузка `.png`, `.jpg`, `.jpeg`, `.gif`, `.svg` и других форматов изображений запрещена.
2. **Цветность:** если цвет на схеме, графике или фото конспекта не несет смысловой нагрузки, картинка должна быть **обесцвеченной (черно-белой)** — это убирает цветовой шум и заметно уменьшает вес файла.
3. **Разрешение:** рекомендуется не более **1500 px** по большей стороне (более высокое разрешение для конспектов и схем не требуется).
4. **Стандарт имени файла:**  
   Имя строится из полного пути от корня репозитория (через `_`), идентификатора заметки (`<ПРЕФИКС>-<НОМЕР>`) и порядкового номера картинки внутри этого конспекта:
   ```text
   <путь_от_корня_через_>_<ПРЕФИКС>-<НОМЕР>_<номер_картинки>.webp
   ```
   * ✅ *Пример для `1-sem/physics/1-LEC_MalyshevaDA/LEC-10_real_gases.md`:*  
     `1-sem_physics_1-LEC_MalyshevaDA_LEC-10_1.webp`
   * ✅ *Пример для `1-sem/physics/1-LEC_MalyshevaDA/LEC-11_surface_tension.md` (вторая картинка):*  
     `1-sem_physics_1-LEC_MalyshevaDA_LEC-11_2.webp`
   * ✅ *Пример для вложенной папки `1-sem/physics/4-TST_MalyshevaDA_2026/1_mechanics/TST-02_dynamics.md`:*  
     `1-sem_physics_4-TST_MalyshevaDA_2026_1_mechanics_TST-02_1.webp`

### 4.3. Ограничения файлов (Размер и расширения)

Система контроля версий (Git) не предназначена для хранения тяжелых бинарных файлов.

1. **Белый список форматов:** К загрузке в репозиторий допускаются исключительно:
   * Документы: **`.md`**, **`.pdf`**
   * Изображения: **`.webp`**  
   Попытка загрузить файл с любым другим расширением (например, `.png`, `.jpg`, `.txt`, `.docx`) вызовет ошибку валидации.
2. **Лимиты по размеру:**
   * **`.pdf`** — максимум **1 МБ**.
   * **`.webp`** — максимум **1 МБ** (в идеале сжимать до **500 КБ**).
   * **`.md`** — максимум **1 МБ**.
3. **Тяжелые PDF (> 1 МБ) и методички преподавателей:**  
   Файлы `.pdf` размером больше 1 МБ загружать в основной репозиторий запрещено. Если вам нужно добавить учебник, методичку или сборник заданий большего объема — напишите мейнтейнерам. Мы выкладываем такие материалы через релизы в отдельном репозитории ассетов [vlsu-hub/assets](https://github.com/vlsu-hub/assets/), после чего в конспект вставляется прямая ссылка на скачивание.
4. **Запрещенные медиаформаты:**  
   Видеофайлы (`.mp4`, `.avi`), аудиозаписи лекций (`.mp3`, `.m4a`, `.wav`), архивы (`.zip`, `.rar`) и презентации (`.pptx`) загружать в репозиторий **запрещено**.  
   * *Решение:* либо так же присылайте ссылку мейнтейнерам, либо загружайте такие материалы на облачные хранилища (Яндекс.Диск, Google Drive) и вставляйте в markdown-файл публичную ссылку.
